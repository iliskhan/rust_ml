# Практика RustML: модель данных и границы доверия

Статус: проект схемы от 12 октября 2026, дополнен внедрением 13 октября.
[practice-schema.sql](practice-schema.sql) — первоначальный проект; действующие
миграции находятся в `learning-lab/supabase/migrations/`. Все три файла целиком
применены к Supabase project `phnjcmahugetofwvnbto` после pristine preflight.
Hosted catalog smoke и анонимный Data API прошли. Два одноразовых аккаунта с
настоящими JWT прошли 10/10 групп hosted-проверок: RLS, CAS, изоляция прогресса,
refresh/logout и выключенный grading. Публичный GitHub OAuth вход проверен отдельно
на опубликованном Pages. UI cloud save/load/reload/logout и повторный вход прошли;
desktop/mobile осмотрены без overflow и ошибок консоли.
Edge API и исполнитель кода ученика не развёрнуты; серверный зачёт отключён.
[Переносимый отчёт приёмки](../evidence/auth-progress/hosted-20261013.json)
содержит миграции, hosted API/Auth, браузерную проверку и deployment.

Зафиксированное решение пользователя: основной язык выбирает ученик. Python,
JavaScript и Rust имеют отдельные решения и результаты. Основной язык определяет
завершение темы; прохождение остальных даёт отдельные достижения. Переключение языка
не переносит успешную попытку на другой язык и не удаляет историю.

Область этой схемы — серверно проверяемые задачи с исходным кодом. Существующие
вопросы на понимание, выбор ответа и ручной численный прогноз перед кодом остаются
локальными учебными самопроверками; они не создают `graded` attempt и не дают
подтверждённый балл. Если требование называется «формула», здесь это маленькая
функция, вычисляющая формулу, а не новый тип сохраняемого quiz. Сохранение и
серверная проверка отдельных choice/numeric quiz в эту схему не входят.

## Сущности

Все имена ниже имеют префикс `practice_`; таблицы находятся в `public`, кроме явно
указанных `private`. UUID идентифицирует конкретный объект релиза, а стабильный
`topic_key` / `exercise_key` связывает соответствующие объекты разных релизов.

| Таблица | Что хранит | Важная граница |
|---|---|---|
| `profiles` | Ссылку на `auth.users.id`, предпочтительный язык | Нет паролей, email или копии JWT; удаляется вместе с Auth user |
| `releases` | Версию набора практики, `draft/published`, дату публикации | Публикация замораживает весь релиз |
| `topics` | Ключ темы, заголовок, порядок, якорь урока | Имеет собственный UUID в каждом релизе |
| `requirements` | Группу эквивалентных задач, обязательность, правило `pass/independent` | Все обязательные группы темы нужны; внутри группы достаточно одного подходящего результата |
| `exercises` | Маленькую учебную задачу, цель, условие, порядок, ссылку на requirement | Несколько равноценных задач могут закрывать одно требование |
| `variants` | Вариант упражнения на одном языке, стартовый код, публичные тесты, entrypoint, runtime digest | В опубликованном релизе каждому упражнению соответствуют все три языка |
| `private.bundles` | Закрытые проверочные тесты, runner spec, подсказки, эталон, hash пакета | Ни Data API, ни браузер не получают эту таблицу |
| `enrollments` | Участие пользователя в конкретном релизе и основной язык | Новый релиз не переписывает прежнюю программу ученика |
| `sessions` | Постоянную пару пользователь + языковой вариант | Новая вкладка не обнуляет помощь и не создаёт вторую облачную версию черновика |
| `drafts` | Текущий код, revision, время сохранения, происхождение `starter/editor/guest_import` | Сохранение проверяет ожидаемую revision |
| `help_receipts` | Первое открытие каждой подсказки/эталона в сессии | Только сервер одновременно записывает факт и выдаёт помощь |
| `attempts` | Неизменный код отправки, hashes, помощь, состояние и проверенный результат | Пользователь не может выставить `pass` или записать тестовые баллы |
| `private.jobs` | Надёжную очередь, аренду, поколение исполнителя, hash результата | Одна задача очереди на попытку; нет второй конкурирующей очереди |

Отдельные таблицы баллов, процентов, достижений, событий каждого нажатия и
«завершённых тем» для первого этапа не нужны. Представление
`practice_topic_progress` пересчитывает прогресс из попыток и состава релиза.
При подтверждённой проблеме производительности можно добавить серверный кэш,
сохранив попытки первичным доказательством и возможность полного пересчёта.

## Версии и публикация

Редактор создаёт новый `draft`-релиз и наполняет его темами, упражнениями, вариантами
и закрытыми пакетами. Всего схема содержит 13 таблиц. Доступ к draft существует только у доверенного процесса
публикации. Публичные RLS-политики пропускают только опубликованные релизы.

`publish_practice_release` проверяет наличие тем, обязательных требований в каждой
теме, хотя бы одной задачи в каждой группе, минимум двух равноценных задач для
каждого `independent`-требования, трёх языковых вариантов и закрытых пакетов. Триггеры запрещают изменение
или удаление опубликованного релиза и его дочернего содержимого; блокировка строки
релиза сериализует публикацию с параллельной редактурой. Процесс публикации также
должен проверить ссылки на реальные уроки, curriculum coverage, эталонные решения
на всех runtime, отрицательные примеры, численные допуски и hashes артефактов.
Эти педагогические и файловые проверки нельзя доказать одним SQL CHECK.

Изменение тестов, эталона, условия или runtime требует нового релиза. Попытка
ссылается на прежний variant/release и хранит `source_sha256`, `bundle_sha256`,
`runtime_digest`. Runtime задаётся digest образа, а не изменяемым тегом `latest`.
Старые образы и пакеты сохраняются, пока нужны воспроизводимость и поддержка
активного релиза. Политика закрытия устаревшего релиза — отдельная будущая миграция;
в данном проекте опубликованный релиз остаётся доступным.

Hash пакета задаёт доверенная сборка: канонический manifest включает тесты, harness,
версию протокола, язык, entrypoint, profile, adapter/compiler flags, численные
допуски и runner spec. `grading_tests` содержит помеченные публичные и скрытые
проверки; публичные примеры не заменяют весь набор. SQL проверяет формат, но не доказывает соответствие
внешнему артефакту. Исполнитель до запуска проверяет digest фактически полученного
пакета и runtime. Нельзя считать совпадение названия файла проверкой целостности.

## Доступ и Supabase Auth

Первоначально планировался email OTP; по выбору владельца 2026-10-13 для
публикации используется GitHub PKCE. OAuth app создан, GitHub provider включён,
Site URL и точный redirect сохранены. Реальный GitHub callback → Pages PKCE
подтверждён браузером; два одноразовых аккаунта через Auth Admin API проверили
серверный JWT/RLS/CAS и удалены после теста. Финальный сценарий работы черновика
в UI также пройден: версия 1 после save, сохранённая сессия после reload,
осознанная замена локального текста серверным и точный starter в версии 2 после
повторного входа.
Это не меняет правила владения SQL ниже. Неавторизованный гость
имеет только локальные черновики. Это не Supabase anonymous Auth user:
у последнего роль `authenticated`, что отличается от роли `anon` обычного
посетителя. [Supabase: RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

| Субъект | Чтение | Запись / выполнение |
|---|---|---|
| `anon` | Опубликованные релизы, темы, упражнения, публичные варианты | Нет облачных записей и серверной проверки |
| `authenticated` | Публичный контент, только свои профиль, enrollment, сессии, черновики, помощь, попытки и прогресс | Только `preferred_language` своего профиля напрямую |
| `practice_api` | Только результаты специально выданных функций | Старт сессии, выбор основного языка, сохранение, открытие помощи, отправка |
| `practice_worker` | Только payload выданного job | Claim, renew, finish; не публикует содержание и не редактирует черновики |
| Процесс публикации / migration owner | Авторские и закрытые данные | Подготовка и публикация релизов |
| Sandbox с кодом ученика | Явно выданные входные данные одного запуска | Нет БД, Supabase, облачных credentials или управления job |

`private` исключается из Exposed schemas в Data API. Все привилегированные функции
лежат там, используют `SECURITY DEFINER SET search_path = ''`, квалифицированные
имена таблиц и адресные `GRANT EXECUTE`. Общий `PUBLIC EXECUTE` отозван.
Функции с `p_user` вызываются доверенным backend через выделенное соединение;
`p_user` извлекается из проверенного access token, никогда из тела запроса.
Backend проверяет токен поддержанным Supabase методом и состояние аккаунта;
локальное декодирование JWT не является проверкой подписи/сессии.
[Supabase: database functions](https://supabase.com/docs/guides/database/functions)

DDL создаёт две `NOLOGIN NOBYPASSRLS` роли без паролей. При внедрении отдельно
настраиваются секретные login credentials, которым выдаётся ровно одна нужная
роль; это не выполняется данным проектом. Если выбран Edge runtime, его доступ
к Postgres/pooler нужно проверить в инфраструктурном прототипе. Закрытая функция
не становится доступной через `supabase.rpc()` только потому, что создана в БД.
Нельзя для удобства выставить `private` в Data API или дать worker роль клиенту.

RLS включена на всех таблицах; grants выдаются отдельно. В этой схеме намеренно
отозваны старые возможные grants `service_role` на новые таблицы/функции. При этом
`service_role` обладает обходом RLS: перенос его ключа в браузер или sandbox
разрушает границы всего проекта, даже если конкретная таблица сейчас закрыта.
Представление прогресса использует `security_invoker = true` (PostgreSQL 15+),
чтобы применять права и RLS вызывающего пользователя.
[Supabase: grants, RLS и views](https://supabase.com/docs/guides/database/postgres/row-level-security)

Составные внешние ключи связывают draft/help с владельцем session, а attempt — с
точной четвёркой session/user/variant/release. Нельзя привязать свою попытку к
чужому черновику или варианту из другого релиза. Эти ограничения действуют также
для доверенных ошибок backend. Владение аккаунтом проверяется по первичному ключу
`auth.users.id`, как рекомендует
[Supabase: user data](https://supabase.com/docs/guides/auth/managing-user-data).

## Черновик, offline и повторная отправка

1. `start_practice(user, variant)` идемпотентно создаёт профиль, enrollment, сессию
   и начальный черновик. При первом enrollment основной язык берётся из профиля;
   новый профиль получает язык выбранного variant. Последующая смена явно
   выполняется через `choose_practice_language`.
2. Клиент загружает `source/revision`, редактирует локально и сохраняет через
   `save_practice_draft(user, session, expected_revision, source, origin)`.
3. SQL атомарно обновляет строку только при совпадении revision и увеличивает её.
   Клиент нормализует draft_conflict_or_not_found к PracticeCloudError status409;
   фактический HTTP-код PostgREST ещё требует hosted-проверки. UI сохраняет обе
   версии и предлагает выбрать или объединить; автоматическое «последний
   записавший победил» не применяется.
4. Для отправки клиент сначала получает подтверждение сохранения и сохраняет UUID
   `idempotency_key` вместе с revision в IndexedDB. Затем вызывает submit с этими
   значениями. Reload и сетевой retry повторяют ту же пару key/revision.
5. `submit_practice` замораживает сохранённый код, вычисляет SHA-256 на сервере,
   закрепляет пакеты/помощь и создаёт attempt + job в одной транзакции.
   Ответ — `attempt_id`; повтор не создаёт новую попытку. Тот же key для другой
   session/revision даёт конфликт, включая отсутствующую (`NULL`) revision.

Параллельные отправки одного пользователя сериализует блокировка профиля. Значения
лимитов в SQL — предложение для MVP: две незавершённые проверки одновременно,
10 отправок за скользящую минуту, 200 за скользящие 24 часа. Завершившаяся ошибкой
инфраструктуры попытка исключается из суточного лимита; минутный защитный лимит
сохраняется. Идемпотентный повтор возвращается до проверок лимитов. Дополнительно
API ограничивает размер тела, частоту по IP/аккаунту и общее число jobs системы.

Гость сохраняет код в IndexedDB с ключом release/variant/language. После входа
импорт идёт тем же optimistic-save с `origin = guest_import`. Локальные результаты,
чужой attempt_id, проценты и отметки «пройдено» не импортируются. Если в облаке уже
есть код, UI показывает конфликт. Только новая серверная проверка импортированного
кода создаёт подтверждённый результат. Достижение собственной работы при этом
не является прокторингом: сервер учитывает предоставленные им подсказки, но не
может доказать отсутствие внешней помощи.

При отсутствии сети разрешено редактировать и выполнять доступные локальные
публичные проверки. Они помечены как предварительные. Серверная отправка ждёт
подтверждённого сохранения; UI показывает непереданные изменения, не фальшивый
облачный успех. Для первого этапа достаточно polling активной попытки с backoff;
Realtime, CRDT и совместное редактирование не требуются.

## Подсказки и статус самостоятельности

Подсказки и эталон выдаёт `open_practice_help`, которая сначала блокирует session,
проверяет существование ключа помощи, записывает receipt и лишь затем возвращает
текст. Повторное открытие не дублирует запись. Отправка использует ту же блокировку,
поэтому нельзя одновременно получить решение и отправить новый код без учёта
помощи из-за гонки транзакций.

В attempt фиксируется `none`, `hint` либо `solution` на момент отправки. Помощь,
открытая после замораживания кода, не меняет прошлую попытку. Новые попытки той же
session учитывают уже открытую помощь. Самостоятельный успешный результат
сохраняется при последующем открытии эталона или неудачных запусках. Отдельная
новая session ради «сброса подсказок» невозможна: `(user_id, variant_id)` уникальна.
Для контрольной группы с правилом `independent` заранее публикуются минимум два
эквивалентных упражнения A/B. После помощи в A ученик получает B с отдельным
variant и собственной историей помощи. Самостоятельное решение B закрывает ту же
группу; решение всех вариантов не требуется. Это конечный авторский банк, а не
непроверенный генератор случайных задач. Если помощь открыта во всех вариантах,
UI честно сообщает: «Выполнено с помощью; самостоятельная проверка пока недоступна».
Чтение следующих тем остаётся доступным. Автор расширяет банк в новом релизе,
переход в который не переносит автоматически старые pass. Удаление receipts ради
восстановления самостоятельности недопустимо.

## Очередь и финализация

SQL-очередь — `private.practice_jobs`. `FOR UPDATE SKIP LOCKED` позволяет нескольким
доверенным исполнителям брать разные строки без ожидания занятой строки; это
подходящий сценарий для очереди, но не обещание согласованного снимка произвольных
данных. [PostgreSQL: SELECT](https://www.postgresql.org/docs/16/sql-select.html)

| Функция worker | Договор |
|---|---|
| `claim_practice_job()` | Берёт готовый queued или просроченный leased job, увеличивает generation, выдаёт новый UUID token и lease на 60 секунд; возвращает закреплённые код, hashes, tests, runner spec |
| `renew_practice_job(job, token, generation)` | Продлевает только действующую непросроченную аренду; `false` означает потерю владения |
| `finish_practice_job(job, token, generation, outcome, passed, error, feedback)` | Проверяет аренду и допустимость результата, атомарно обновляет attempt + job; возвращает состояние попытки |

Worker supervisor регулярно продлевает lease, а процесс с кодом ученика этого
интерфейса не видит. После аварии другой worker получает новое поколение и token.
Ответ старого worker отвергается, даже если вычисление завершилось успешно.
Повтор finish с тем же token/generation и hash уже принятого результата безопасен;
другой результат отвергается. Lease, который истёк до finish, не принимается.
Обработка может повториться; публикация результата одной попытки принимается
не более одного раза. Это не обещание exactly-once выполнения кода.

`outcome = pass/fail` даёт `graded`. Ошибки компиляции/исполнения, time/memory/output
limit относятся к работе ученика и дают `graded + fail`; соответствующие counts
проверяет SQL. `outcome = infrastructure` повторяет тот же job через 5 секунд до
трёх получений lease. Затем attempt становится `error/infrastructure`; это не
учебный провал. Просроченный третий lease также завершается инфраструктурной
ошибкой при очередном claim. Для очистки просроченных задач должен работать хотя
бы один worker; зависшая инфраструктура показывается в мониторинге.

SQL хранит только ограниченный по размеру `feedback`, уже очищенный доверенным
supervisor. Секретные входы, expected outputs, скрытые имена тестов, filesystem
paths и произвольные stack traces не должны туда попадать. Решение ученика не
может само сформировать достоверный «pass»: supervisor проверяет протокол и итог
доверенного harness. Полный sandbox/протокол описан в
[practice-execution.md](practice-execution.md).

## Как считается прогресс

Для каждого `(user, release, topic, language)` представление считает требования,
а не попытки или все альтернативные задания. Внутри requirement действует OR:
достаточно одного exercise с подходящим pass. Между обязательными requirements
действует AND. Для обычной практики (код для формулы, реализация, крайний случай)
`completion_rule = pass` допускает помощь; контроль переноса использует
`completion_rule = independent` и требует pass без подсказок и эталона именно
этого варианта. Повторы не увеличивают числитель, а запасные A/B не увеличивают
знаменатель. Optional группы имеют отдельные total/passed.

Пример: четыре обязательные группы (код для формулы, реализация, крайний случай, перенос)
и одна optional; перенос содержит задачи A/B. Первые три выполнены с подсказками,
A — с эталоном, B — самостоятельно. Получается 4/4 выполненных требований,
1/1 самостоятельных контрольных требований; optional показана отдельно.

`required_passed` — группы с любым серверным pass, `required_completed` — группы
с результатом, удовлетворяющим их правилу. Тема завершена при `required_total > 0`
и `required_completed = required_total` в строке `is_primary_language = true`.
`independent_required_total/passed` отдельно показывают контрольные требования.
Две другие языковые строки являются основанием отдельных достижений. UI явно
различает «все задания проверены» и «самостоятельный контроль пройден».

`choose_practice_language(user, release, language)` меняет основной язык конкретного
enrollment и обновляет предпочтение для будущих enrollment. При переходе с Python
на Rust экран основного прогресса показывает Rust; Python-результат остаётся как
достижение. Новые обязательные упражнения нового релиза не уменьшают знаменатель
или процент старого релиза задним числом. Переход на новый релиз требует явного
выбора; автоматическое копирование pass не предусмотрено.

## Удаление аккаунта и эксплуатация

FK `profiles.user_id -> auth.users.id ON DELETE CASCADE` удаляет enrollment,
session, draft, receipts, attempts и jobs. Backend сначала останавливает новые
отправки и инициирует отмену активных sandbox; окончательное удаление Auth user
удаляет и БД-данные. Если worker вернулся после удаления, его finish получает
`job_not_found`; он очищает локальные файлы и ничего не восстанавливает.

Уже выданный access token не становится мгновенно криптографически невалидным
после удаления аккаунта. Поэтому защищённый API проверяет состояние пользователя,
а FK не позволяет `start_practice` заново создать профиль отсутствующего
`auth.users`. Очистка внешних Storage-объектов и sandbox-дисков выполняется отдельно;
эта схема не создаёт Storage buckets. Исходники, токены, тесты и эталоны не пишутся
в обычные логи. [Supabase: удаление пользователей](https://supabase.com/docs/guides/auth/managing-user-data)

Deadlock/serialization failure транзакции можно ограниченно повторить целиком с
тем же idempotency key; это особенно важно при одновременном account deletion и
worker finalize. Ошибка после неизвестного исхода submit сначала разрешается
повтором исходного запроса, а не созданием нового ключа.

## Проверка перед внедрением

На 12 октября 2026 выполнен статический разбор схемы и договоров; тогда DDL ещё
не выполнялся. 13 октября pristine preflight подтвердил отсутствие конфликтов,
целые миграции 001→003 выполнены на hosted PostgreSQL через session pooler с
проверкой TLS по CA проекта. Независимый smoke проверил 17 SQL-наборов, 13 RLS
таблиц и seed; anon HTTP подтвердил публичное чтение и отказ для `private`.
Локальный PGlite smoke с `auth.uid` stub проверил 12403 утверждения. Реальные
JWT/RLS/CAS затем проверены с двумя временными пользователями: 10/10 hosted групп
PASS, включая одновременный HTTP CAS (один успех, один конфликт), чужие записи,
408 изолированных строк прогресса на аккаунт, refresh/logout. Тестовые аккаунты
удалены. Финальная UI-приёмка черновика и mobile прошла; cloud версия 2 содержит
точный starter без тестовых маркеров. Доказательства сведены в
[переносимом отчёте](../evidence/auth-progress/hosted-20261013.json).
Ниже сохранены проектные критерии схемы. Сценарии submit, verdict, очереди и
worker относятся к будущему runner и не заявлены как hosted-приёмка: production
grading выключен. Они не блокируют уже принятые Auth, черновики и прогресс.

| Сценарий | Ожидаемый результат |
|---|---|
| Применить SQL в transaction на PostgreSQL 15+ | Созданы 13 таблиц, функции, индексы и RLS; нет неожиданных grants |
| Опубликовать неполный релиз; затем полный | Неполный отвергнут; полный читается anon; draft не читается |
| Изменить/удалить опубликованный вариант или bundle | Отказ; параллельная публикация не пропускает изменение |
| A читает / меняет записи B и вызывает private функции через REST | Нет данных / отказ; private не exposed |
| authenticated пишет `attempts.verdict`, score или receipt | Отказ по grants; view не раскрывает чужие строки |
| Две вкладки сохраняют одну revision | Ровно одно сохранение, второй запрос отклонён, клиентский status409; raw HTTP-код проверить отдельно, код второго остаётся локально |
| Два одновременных submit с одним key/revision | Один attempt, один job; один и тот же attempt_id |
| Повторить key с иной session/revision или NULL revision | Конфликт; новая попытка не появляется |
| Одновременно раскрыть solution и отправить сохранённый код | Порядок сериализован; receipt до submit учитывается, после submit не меняет прошлый снимок |
| Два worker делают claim; один lease истекает и переходит другому | Нет двух действующих владений; старый token/generation не может renew/finish |
| Finish дважды; затем с изменённым verdict; затем с NULL generation | Идентичный повтор безопасен, остальные отвергнуты |
| Finish с `pass`, но неполными тестами или learner error | CHECK отвергает несовместимый результат |
| Worker упал после claim / после commit finish | Lease восстановим / повтор не дублирует прогресс |
| Три инфраструктурные ошибки либо три истёкших lease | `error/infrastructure`, без учебного fail и расхода суточного лимита |
| Повторы, optional, смена основного языка, новый релиз | Знаменатели и прежние результаты остаются корректными |
| Контроль A с подсказкой, B без помощи в одной requirement | A остаётся assisted, B закрывает independent requirement; оба не дают двойного прогресса |
| Independent requirement с одним упражнением при публикации | Публикация отвергнута: нужен начальный банк минимум A/B |
| Импорт гостевого кода с локальным `pass=true` | Сохраняется только код/provenance, облачный pass отсутствует до проверки |
| Удаление auth user одновременно с job; запрос старым JWT | Персональные строки/queue удалены; новый профиль по удалённому id невозможен |

Миграции уже применены к выбранному проекту; слепой повторный запуск может
столкнуться с созданными ролями и объектами. Прямое SQL-применение не создало
CLI migration ledger. Будущие runner/worker сценарии проверять без повторного DDL;
настройку runner и серверных credentials выполнять отдельным этапом.
